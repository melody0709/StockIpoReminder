# 主页更新横幅、静默提醒与检查节奏优化方案

- 状态：待评审（本方案只描述改动，不含已实施内容）
- 记录日期：2026-09-17
- 产品版本事实来源：`Cargo.toml`（当前工作区为 `0.3.9`）
- 前置方案：`.plan/feat/certificate-free-minisign-auto-update.md`（信任模型、schema v2 清单、helper 安装闭环，本方案不修改其安全边界）
- 参考项目：`changexbc/workbuddy-switch`（Tauri 2 + `tauri-plugin-updater`，MIT）

## 1. 需求

1. 发现更新时**不再弹出 Windows Toast / 托盘气泡**。
2. 有更新时在**主页**直接提示，并提供**绿色的一键更新按钮**，不必每次进设置页手动操作。
3. 结合参考项目的做法，找出可以学习与优化的点。

## 2. 现状与参考项目对照

| 维度 | 本项目 `stock_new` | `workbuddy-switch` | 评价 |
| --- | --- | --- | --- |
| 技术栈 | Rust + Slint 单 EXE，WiX MSI | Tauri 2 + React | 不可照搬实现，可借鉴交互 |
| 信任根 | 自建 Minisign 公钥，schema v2 清单签名字节 | `tauri-plugin-updater` 内置 `pubkey`（同为 Minisign 体系） | **选型一致**，互相印证 |
| 清单形态 | `update-manifest.json` + `.minisig`，含版本/时间/Build/资产名/大小/SHA-256 | `latest.json`（合并各平台），`platforms` 内含签名与 URL | 我们更严（多字段校验 + 常量时间外的大小上限） |
| 发现渠道 | 固定 `releases/latest/download/update-manifest.json` | 同一路径 + `latest-{{target}}-{{arch}}.json` 兜底 + **302 Location 解析 tag 兜底** | 他们的兜底值得借鉴 |
| 检查节奏 | 启动延迟 3s + 每小时定时器，**24 小时**节流才发请求 | 启动检查 + **30 分钟**轮询，成功结果**进程内缓存 6 小时**（命中不发请求） | 发现延迟从 ≤24h 降到 ≤6h，网络成本仍极低 |
| 下载/安装 | 下载到受控 pending → 用户点击「重启并更新」→ helper + supervisor 互斥量 + `msiexec` | 应用内 `downloadAndInstall`（Tauri 进程内安装）→ `relaunchApp` | 我们的进程时序更稳（Watchdog/TOCTOU/pending 恢复） |
| 交互入口 | 设置页「高级与维护」卡片 + 更新 Toast | 侧栏版本号旁的**小圆形 ↑ 按钮** + 模态对话框（无任何系统通知） | **正是本次要改的方向** |
| 进度展示 | 按钮文案上的百分比 | 百分比 + 已下载/总大小 + 可点击的下载地址 + 重试/打开 Release | 借鉴其进度与失败兜底 |
| 失败打扰 | 状态文字显示错误 | 静默（`catch` 后不打扰） | 借鉴：自动检查失败不进入用户视野 |
| 网络受限 | 无代理能力 | 更新源可配 `proxy`（`github_config.json`） | 国内访问 GitHub 的痛点，值得列为可选增强 |

结论：安全与安装链路我们更强，**交互与发现节奏明显弱于参考项目**——不弹窗、发现即用、失败可自救，这三点是本次要补的。

## 3. 目标体验

1. 程序发现新版本时不弹任何系统通知；用户打开主窗口即可看到绿色更新入口。
2. 从「看到」到「升级完成」只需在同一位置点击两次（下载 → 重启并更新），不需要进设置页。
3. 检查更新在无人操作时最多每小时做一次轻量判断、每 6 小时最多一次真实网络请求。
4. 更新源不可用（国内网络常见）时，用户仍能一键打开发布页手动下载，且不会出现任何自动安装入口。

## 4. 设计

### 4.1 通知策略：更新类通知全部去掉

- `UpdateController::update_notifier` 不再调用 `tray.notify`（Toast 与气泡回退一并移除）；更新流程不再读取 `settings.toast_enabled`。
- 保留的提示渠道（均为被动、不打断）：
  - 主页更新横幅（见 4.2）；
  - 托盘右键菜单中的动态项（见 4.3）；
  - 设置页更新卡片（原有入口保留，作为高级用法）。
- `update-state.json` 中 `lastNotifiedVersion` 的语义改为「该版本已在横幅提示过」，用于避免重复强调，不再触发弹窗。
- 更新其他提醒（打新提醒、健康摘要、崩溃报告）完全不受影响。

### 4.2 主页更新横幅与「一键更新」按钮

位置：主窗口**状态行下方、导航行上方**（全局可见，四个页面都能看到），窄窗口下改为两行自适应，不使用固定高度以免再次出现裁切。

状态机与按钮文案：

```text
                    ┌──────────── 无更新：横幅整行不渲染 ────────────┐
idle ────────────────────────────────────────────────────────────► (隐藏)

available  横幅：「发现新版本 0.3.10 · 修复设置页显示问题」  按钮：一键更新（绿）
           └─点击→ downloading
downloading 横幅：「正在下载更新 0.3.10 · 42%（3.1 MB / 7.4 MB）」 按钮：下载中 42%（禁用）
           ├─完成→ ready
           └─失败→ failed
ready      横幅：「0.3.10 已下载并验证，重启后生效」          按钮：重启并更新（绿）
           └─点击→ installing（程序退出，交给 helper）
failed     横幅：「更新下载或验证失败：<可读原因>」            按钮：重试（绿）
                                                    次级按钮：手动下载（打开 Release）
```

规则：

- **绿色按钮只有一个**，位置固定，随状态换文案，符合「一键更新」的心智模型；下载与安装仍分两步，第二次点击前程序绝不退出（保持前置方案第 5.3 节第 10 条与第 7 节的边界）。
- 横幅右侧提供「稍后」次级按钮：仅隐藏当前版本横幅，把 `bannerDismissedVersion` 写入 `update-state.json`；设置页入口与托盘菜单项仍然可见。新版本出现时横幅重新出现。
- 「手动下载」次级按钮复用已实现的 `open-release-notes` 同款安全外链能力（仅允许无凭据 HTTPS）。
- 带宽与磁盘：下载中显示百分比与「已下载/总大小」，失败原因保持脱敏后展示。
- 待安装状态在应用重启后由现有 `restore_pending` 恢复，横幅直接进入 `ready`，无需重新下载。

### 4.3 托盘侧被动入口

- 托盘右键菜单在有可用更新时插入一项：`发现新版本 0.3.10…`（`MF_STRING`，位于「打开主窗口」之后），点击只打开主窗口并定位到主页横幅。
- 不新增托盘气泡、不改托盘图标外观、不做图标角标（避免与「不打扰」目标冲突）。
- 托盘菜单已是每次重建，新增动态项不需要新的状态通道。

### 4.4 检查节奏与缓存（借鉴参考项目）

- 新增**成功结果缓存**：清单校验通过的结果在进程内缓存 6 小时；自动轮询命中缓存时**不发网络请求**。
- 自动检查节奏改为：启动延迟 3 秒 + 每 30 分钟到期判断；真实网络检查受 6 小时缓存约束（等价于每天最多 4 次请求，优于当前 24 小时一次的体验）。
- 手动检查继续 `force` 绕过缓存与节流。
- 失败不写缓存、不改变下次自动检查节奏；自动检查失败只写脱敏日志（与参考项目的静默策略一致），不再更新界面状态文字；手动检查失败仍在横幅/设置卡片显示可读原因。
- 该改动修订前置方案 6.3 的「24 小时节流」表述，需同步更新 `.plan/feat/certificate-free-minisign-auto-update.md` 与 `README.md`。

### 4.5 弱网兜底：只提示、不安装

- 主路径不变：签名清单是唯一可进入安装流程的材料。
- 新增只读兜底：清单或签名拉取失败时，可选地请求 `https://github.com/<owner>/<repo>/releases/latest` 并**不跟随重定向**，从 302 `Location` 解析出 tag（形如 `v0.3.10`）。
  - tag 高于当前版本 → 横幅提示「无法验证更新清单；发现 0.3.10，可手动下载」，主按钮变为「打开下载页」（普通外链，不进入自动安装）。
  - tag 无法解析、网络失败或 tag 不高于当前版本 → 保持静默（不打扰）。
- 兜底结果**永不**参与版本比较之外的任何判断，也不写入 pending、不触发下载。

### 4.6 可选增强：更新源代理

- 需求来源：参考项目为国内用户提供 `proxy` 配置；本项目更新源固定为 GitHub，弱网/被墙时体验差。
- 建议列为独立可选阶段：新增设置项 `update_proxy_url`（默认空），仅用于更新模块的 HTTP 客户端（`updater::update_client`），接受 `http(s)://` 与 `socks5://`，拒绝含用户名/密码的 URL，不写入日志与诊断包。
- 若评审认为当前不需要，可整条延后，不影响 4.1～4.5 的交付。

## 6. 明确不改的东西

- 信任根、schema v2 清单字段与校验顺序；`allow_legacy=false`。
- 受控 pending 目录、helper 只接收 `data_root` + 父进程 PID、MSI 只读锁定、supervisor 互斥量等待、失败保留可重试 pending 与拉起当前版本。
- 「下载」与「安装」两步分离；任何情况下都不静默安装、不绕过 UAC。
- 便携版不支持应用内更新。

## 7. 验收门槛

自动化与人工至少覆盖：

- 更新流程内不存在任何 Toast/气泡调用路径（代码审查 + smoke 断言）。
- 无更新时横幅完全不渲染，主界面布局与现有页面在两个维度（宽度/高度紧凑）下都不出现裁切。
- `available → downloading → ready → installing` 全链路在同一按钮上完成，进度显示百分比与已下载/总大小。
- 下载失败后按钮变「重试」且 pending 保留；重启应用后 `ready` 状态由 `restore_pending` 恢复，横幅直接进入可升级状态。
- 「稍后」只隐藏当前版本，重启后仍隐藏；发布更高版本后横幅重新出现。
- 清单拉取失败且 302 兜底发现更高版本时，只出现「打开下载页」，**不出现任何会自动安装的按钮**。
- 6 小时缓存生效：同一进程内 6 小时内第二次自动检查不发网络请求（单测）；手动检查 `force` 生效。
- `rtk cargo fmt`、`rtk cargo test`、`build.bat --package`、`validate-build-layout.ps1`、smoke、篡改测试、release audit 全绿。

## 8. 实施顺序

1. **P0**：去掉更新 Toast + 主页横幅与绿色一键更新按钮（含「稍后」与失败重试）。这是用户最直接的诉求，改动集中在 `background_operations.rs` + `main.slint`。
2. **P1**：检查节奏与 6 小时缓存、302 只读兜底与「手动下载」入口。
3. **P2**：托盘动态菜单项、进度细化（已下载/总大小）。
4. **P3**：可选代理设置（需评审）、文档同步与发布 0.4.0（含 `RELEASE_NOTES.md`）。

## 9. 风险与取舍

- **长期不打开主窗口的用户可能错过更新**：横幅只在主窗口可见，托盘菜单项与设置页是补充；如后续需要，可加「托盘图标绿点」但不做气泡。
- **6 小时缓存与现有 24 小时节流文档冲突**：必须在同一次发布内同步修订，避免文档与行为不一致。
- **302 解析依赖 GitHub 行为**：仅作提示用途，失败静默，不引入新的信任假设。
- **代理设置可能被当作通用代理**：限定更新模块、限定协议、禁止内嵌凭据，日志与诊断包一律不记录。
- **绿色按钮的视觉权重**：需与「立即同步」按钮区分（同为绿/蓝系），避免用户误点；文案必须显式带版本号。

## 10. 明确不做

- 不做静默安装、不做后台强制更新、不绕过 UAC。
- 不做差分更新、不做多通道（stable/beta）、不做自动回滚。
- 不引入 Tauri/WebView，不引入独立更新服务。
- 不为「更新」单独新增状态框架或任务系统（沿用 `UpdateController` 与 `OperationGate`）。
- 不使用任何未签名信息驱动安装。
