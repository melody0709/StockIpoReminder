# 顶部更新胶囊按钮、静默提醒与检查节奏优化方案

- 状态：P0～P2 已实施（0.4.0）；P3 的可选代理尚未实现，仍需评审
- 记录日期：2026-09-17
- 产品版本事实来源：`Cargo.toml`（**2026-09-21 复核：当前工作区为 `0.4.3`**；本文写作时为 `0.3.9`）
- 版本基线更新：P0～P2 已随 **0.4.0** 发布；随后 **0.4.1** 补上「每次启动都重新检查」（唯一例外是距上次检查不足 10 分钟）与托盘「打开发布页」入口，**0.4.2** 仅提升版本号并作为验证一键升级闭环的升级目标版本。正文中出现的 `0.3.9` / `0.3.10` 是写作时的示例版本号，不代表当前版本。
- 前置方案：`.plan/feat/certificate-free-minisign-auto-update.md`（信任模型、schema v2 清单、helper 安装闭环）。本方案不修改其安全边界，但**修订其 §5.3 第 10 条与 §7 的交互约定**：用户点击一次即授权「下载 + 安装 + 重启」，不再要求第二次点击。
- 参考项目：`changexbc/workbuddy-switch`（Tauri 2 + `tauri-plugin-updater`，MIT）

## 1. 需求

1. 发现更新时**不再弹出 Windows Toast / 托盘气泡**。
2. 有更新时在**主页**直接提示，并提供**绿色的一键更新按钮**，不必每次进设置页手动操作。
3. **点击一次即全自动**：自动下载、自动验证、自动退出安装，新版**直接以托盘模式启动**，不再出现第二次「重启并更新」确认。
4. 结合参考项目的做法，找出可以学习与优化的点。

## 2. 现状与参考项目对照

| 维度 | 本项目 `stock_new` | `workbuddy-switch` | 评价 |
| --- | --- | --- | --- |
| 技术栈 | Rust + Slint 单 EXE，WiX MSI | Tauri 2 + React | 不可照搬实现，可借鉴交互 |
| 信任根 | 自建 Minisign 公钥，schema v2 清单签名字节 | `tauri-plugin-updater` 内置 `pubkey`（同为 Minisign 体系） | **选型一致**，互相印证 |
| 清单形态 | `update-manifest.json` + `.minisig`，含版本/时间/Build/资产名/大小/SHA-256 | `latest.json`（合并各平台），`platforms` 内含签名与 URL | 我们更严（多字段校验 + 常量时间外的大小上限） |
| 发现渠道 | 固定 `releases/latest/download/update-manifest.json` | 同一路径 + `latest-{{target}}-{{arch}}.json` 兜底 + **302 Location 解析 tag 兜底** | 他们的兜底值得借鉴 |
| 检查节奏 | 启动延迟 3s + 每小时定时器，**24 小时**节流才发请求 | 启动检查 + **30 分钟**轮询，成功结果**进程内缓存 6 小时**（命中不发请求） | 发现延迟从 ≤24h 降到 ≤6h，网络成本仍极低 |
| 下载/安装 | 下载到受控 pending → 用户点击「重启并更新」→ helper + supervisor 互斥量 + `msiexec` | 应用内 `downloadAndInstall`（Tauri 进程内安装）→ `relaunchApp` | 我们的进程时序更稳（Watchdog/TOCTOU/pending 恢复） |
| 交互入口 | 设置页「高级与维护」卡片 + 更新 Toast | 侧栏版本号旁的**小圆形 ↑ 按钮** + 模态对话框（无任何系统通知） | **正是本次要改的方向** |
| 进度展示 | 按钮文案上的百分比 | 百分比 + 已下载/总大小 + 可点击的下载地址 + 重试/打开 Release | 借鉴其进度与失败兜底 |
| 失败打扰 | 状态文字显示错误 | 静默（`catch` 后不打扰） | 借鉴：自动检查失败不进入用户视野 |
| 网络受限 | 无代理能力 | 更新源可配 `proxy`（`github_config.json`） | 国内访问 GitHub 的痛点，值得列为可选增强 |

结论：安全与安装链路我们更强，**交互与发现节奏明显弱于参考项目**——不弹窗、发现即用、失败可自救，这三点是本次要补的。

## 3. 目标体验

1. 程序发现新版本时不弹任何系统通知；用户打开主窗口即可看到绿色更新入口。
2. 从「看到」到「升级完成」只需**一次点击**：点绿色胶囊后自动下载、验证、退出、安装，新版以托盘模式启动，用户不需要再确认第二次。
3. 检查更新在无人操作时最多每小时做一次轻量判断、每 6 小时最多一次真实网络请求。
4. 更新源不可用（国内网络常见）时，用户仍能一键打开发布页手动下载，且不会出现任何自动安装入口。

## 4. 设计

### 4.1 通知策略：更新类通知全部去掉

- `UpdateController::update_notifier` 不再调用 `tray.notify`（Toast 与气泡回退一并移除）；更新流程不再读取 `settings.toast_enabled`。
- 保留的提示渠道（均为被动、不打断）：
  - 版本徽标旁的绿色更新胶囊按钮与按需细行（见 4.2）；
  - 托盘右键菜单中的动态项（见 4.3）；
  - 设置页更新卡片（原有入口保留，作为高级用法）。
- `update-state.json` 中 `lastNotifiedVersion` 的语义改为「该版本已在界面提示过」，用于避免重复强调，不再触发弹窗。
- 更新其他提醒（打新提醒、健康摘要、崩溃报告）完全不受影响。

### 4.2 顶部绿色「更新」胶囊按钮（Zed 式）

形态与位置（对齐参考项目 `changexbc/workbuddy-switch` 侧栏按钮、以及 Zed 编辑器工具栏的绿色 Update 胶囊）：

- 位置：主窗口**标题行中、紧挨版本徽标 `v0.3.9` 的正右侧**（标题 → 版本徽标 → 绿色更新胶囊），与现有按钮同一行同一高度（38px），圆角胶囊，绿色底 + 深色文字。
- 为什么放这里：更新是「关于当前版本」的信息，紧贴版本号语义最顺；标题行最右侧继续留给操作类按钮（`立即同步` / `隐藏到托盘`），避免把「查看状态」和「执行操作」两类控件混在一起。
- compact 宽度时只保留两字「更新」，避免挤压标题与导航。
- 实现为 `ActionButton` 新增 `positive: true` 变体（绿色），不改变现有 `primary`（蓝）/ `danger`（红）语义。
- 状态解释文字放在**现有状态行之后的一条「按需细行」**（仅 downloading / ready / failed 渲染），不新开常驻行、不用固定高度，避免再次出现 0.3.8 那种裁切。

状态机与文案（同一个按钮换文案，位置固定）：

```text
无更新            不渲染任何更新元素（详见 4.2.1）
available         [更新 0.3.10]                     细行：发现 0.3.10，点击后自动下载并重启升级
                  └─点击（唯一一次确认）→ downloading
downloading       [下载 42%]（禁用）                 细行：3.1 MB / 7.4 MB 的进度条
                  ├─完成并验证通过→ installing
                  └─失败→ failed
ready（上次已下载） [更新 0.3.10]                    细行：更新包已就绪，点击立即重启升级
                  └─点击→ installing
installing        [正在重启更新…]（禁用）             细行：已下载并验证，正在退出并安装
                  └─程序退出 → helper 安装 → 新版以托盘方式启动
failed            [重试]  次级：[手动下载]            细行：更新下载或验证失败：<脱敏原因>
```

规则：

- **绿色按钮只有一个**，随状态换文案。**唯一一次点击即完成全部授权**：下载 → 验证 → 退出 → 安装 → 重启到托盘；此后不再出现任何确认步骤。
- 「稍后」次级按钮（available / ready 显示）：仅隐藏当前版本的更新元素，把 `bannerDismissedVersion` 写入 `update-state.json`；版本徽标入口、设置页卡片与托盘菜单项仍然可见。出现更高版本时重新显示。
- 「手动下载」次级按钮复用已实现的 `open-release-notes` 同款安全外链能力（仅允许无凭据 HTTPS）。
- 进度显示百分比与「已下载/总大小」；失败原因脱敏后展示，更详细的信息可通过版本徽标进设置页查看。
- 设置页原有的「发现更新后自动下载」开关保留：开启后检查到新版本会提前把更新包下载好，用户点击胶囊时无需等待下载，直接进入退出安装；该开关仍默认关闭，只影响**下载时机**，不改变「必须由用户点击才安装」的同意模型。

### 4.2.2 一键全自动的边界与保护

1. **同意模型**：一次点击 = 授权「下载 + 安装 + 重启」。程序不会在没有任何用户点击的情况下安装，也不做后台静默更新。
2. **退出前的收尾**：点击后仍走程序现有的正常关闭路径——先原子落盘设置与窗口尺寸、停运行时任务，再退出事件循环；不在安装中途强杀进程。
3. **重启形态**：helper 以 `msiexec /i ... /passive /norestart` 安装，成功后启动 `StockIpoReminder.exe --background`，即新版**常驻托盘、不弹主窗口**（沿用 0.3.3 起的默认托盘启动行为）。
4. **用户可以中途放弃**：下载过程中仍可正常关闭程序，不阻塞退出；已验证提交的 pending 保留，下次启动胶囊直接进入 ready。
5. **失败与 UAC 取消**：helper 保留可重试 pending，并在释放 supervisor 互斥量后拉起当前版本；下次启动胶囊显示「更新 x.y.z」（或「重试」），用户可再次点击。
6. **升级后的回执**：helper 已写入 `diagnostics/update-last-result.json`，新版启动时在细行做一次性提示（如「已更新到 0.3.10」，5 秒后消失），不需要额外的通知渠道。
7. **不做**：不做倒计时弹窗、不做强制更新、不做「安装前二次确认」——按本方案第 1 节第 3 条，确认只需一次。

### 4.2.1 没有检测到新版本时怎么显示（本次设计决策）

**推荐：不渲染任何更新元素**——没有绿色按钮、没有细行、没有常驻文字。

理由：

1. 绿色胶囊的语义是「现在有事可做」。无动作时保留一个绿色按钮，会让用户反复怀疑是不是漏了新版本，还把「是否最新」变成需要主动确认的问题。
2. Zed、Chrome、VS Code 都是「有待处理更新才出现」；这是用户已经习惯的模式。
3. 标题行已有标题、版本徽标、立即同步、隐藏到托盘四个元素，再常驻一个按钮会挤压窄窗口。

补偿措施（保证手动入口和反馈都不丢）：

- **版本徽标变为可点击**：点击 `v0.3.9` 徽标直接切到「设置 → 高级与维护 → 安全自动更新」区域，那里保留当前版本/可用版本/手动检查/两个开关的完整能力，并在范围内高亮一次。
- **一次性检查反馈**：本次会话中用户**显式触发过检查**（点徽标进设置页后点「检查更新」）且结果是最新时，细行显示「已是最新版本 v0.3.9」，5 秒后自动消失；自动检查结果是最新时保持完全静默，不占用任何界面空间。
- 托盘右键菜单项只在确有更新时出现（见 4.3），因此托盘侧也没有常驻噪声。

被否决的备选方案：

| 方案 | 否决理由 |
| --- | --- |
| 常显绿色按钮，无更新时文案「已是最新」并禁用 | 绿色代表可点，禁用绿色自相矛盾；且常驻占宽，窄窗口挤压 |
| 常显灰色文字「已是最新」 | 比绿色按钮好，但仍是顶部常驻噪声，收益仅是"看起来有反馈" |
| 常显小圆点，有更新变绿 | 含义需要学习；既然版本徽标可以做成入口，不如让徽标本身承担这个职责 |

### 4.3 托盘侧被动入口

- 托盘右键菜单在有可用更新时插入一项：`发现新版本 0.3.10…`（`MF_STRING`，位于「打开主窗口」之后），点击只打开主窗口（此时绿色按钮与细行已可见）。
- 不新增托盘气泡、不改托盘图标外观、不做图标角标（避免与「不打扰」目标冲突）。
- 托盘菜单已是每次重建，新增动态项不需要新的状态通道。

### 4.4 检查节奏与缓存（借鉴参考项目）

- 新增**成功结果缓存**：清单校验通过的结果在进程内缓存 6 小时；自动轮询命中缓存时**不发网络请求**。
- 自动检查节奏改为：启动延迟 3 秒 + 每 30 分钟到期判断；真实网络检查受 6 小时缓存约束（等价于每天最多 4 次请求，优于当前 24 小时一次的体验）。
- 手动检查继续 `force` 绕过缓存与节流。
- 失败不写缓存、不改变下次自动检查节奏；自动检查失败只写脱敏日志（与参考项目的静默策略一致），不再更新界面状态文字；手动检查失败仍在细行/设置卡片显示可读原因。
- 该改动修订前置方案 6.3 的「24 小时节流」表述，需同步更新 `.plan/feat/certificate-free-minisign-auto-update.md` 与 `README.md`。

### 4.5 弱网兜底：只提示、不安装

- 主路径不变：签名清单是唯一可进入安装流程的材料。
- 新增只读兜底：清单或签名拉取失败时，可选地请求 `https://github.com/<owner>/<repo>/releases/latest` 并**不跟随重定向**，从 302 `Location` 解析出 tag（形如 `v0.3.10`）。
  - tag 高于当前版本 → 细行提示「无法验证更新清单；发现 0.3.10，可手动下载」，主按钮变为「打开下载页」（普通外链，不进入自动安装）。
  - tag 无法解析、网络失败或 tag 不高于当前版本 → 保持静默（不打扰）。
- 兜底结果**永不**参与版本比较之外的任何判断，也不写入 pending、不触发下载。

### 4.6 可选增强：更新源代理

- 需求来源：参考项目为国内用户提供 `proxy` 配置；本项目更新源固定为 GitHub，弱网/被墙时体验差。
- 建议列为独立可选阶段：新增设置项 `update_proxy_url`（默认空），仅用于更新模块的 HTTP 客户端（`updater::update_client`），接受 `http(s)://` 与 `socks5://`，拒绝含用户名/密码的 URL，不写入日志与诊断包。
- 若评审认为当前不需要，可整条延后，不影响 4.1～4.5 的交付。

## 6. 明确不改的东西

- 信任根、schema v2 清单字段与校验顺序；`allow_legacy=false`。
- 受控 pending 目录、helper 只接收 `data_root` + 父进程 PID、MSI 只读锁定、supervisor 互斥量等待、失败保留可重试 pending 与拉起当前版本。
- 同意模型：**必须由用户点击一次**才安装；不做无点击的后台静默安装、不绕过 UAC。
- 安装后的启动形态固定为 `--background` 托盘常驻（不改为显示主窗口）。
- 便携版不支持应用内更新。

## 7. 验收门槛

自动化与人工至少覆盖：

- 更新流程内不存在任何 Toast/气泡调用路径（代码审查 + smoke 断言）。
- 无更新时不渲染任何更新元素（无按钮、无细行），主界面布局在宽度/高度两种紧凑模式下都不出现裁切。
- 显式手动检查且结果为最新时，细行显示「已是最新版本」并在 5 秒内自动消失；自动检查为最新时不显示任何元素。
- 版本徽标可点击并切到设置页更新区域。
- **一次点击**完成 `available → downloading → 退出 → installing → 新版托盘启动`，全程无第二次确认；下载中有百分比与已下载/总大小。
- 升级完成后新版本**不弹主窗口**，常驻托盘；细行一次性提示「已更新到 x.y.z」后 5 秒消失。
- 下载中关闭程序不会留下损坏状态；下次启动胶囊直接进入 ready（点击即装）。
- 点击后 UAC 取消或安装失败时，当前版本被重新拉起且胶囊可再次点击。
- 下载失败后按钮变「重试」且 pending 保留；重启应用后 `ready` 状态由 `restore_pending` 恢复，点击即进入安装。
- 「稍后」只隐藏当前版本，重启后仍隐藏；发布更高版本后更新元素重新出现。
- 清单拉取失败且 302 兜底发现更高版本时，只出现「打开下载页」，**不出现任何会自动安装的按钮**。
- 6 小时缓存生效：同一进程内 6 小时内第二次自动检查不发网络请求（单测）；手动检查 `force` 生效。
- `rtk cargo fmt`、`rtk cargo test`、`build.bat --package`、`validate-build-layout.ps1`、smoke、篡改测试、release audit 全绿。

## 8. 实施顺序

1. **P0**：去掉更新 Toast + 标题行绿色更新胶囊与按需细行 + **一次点击后自动下载、退出、安装并重启到托盘**（含「稍后」、失败重试、版本徽标入口）。这是用户最直接的诉求，改动集中在 `background_operations.rs` + `main.slint`。
2. **P1**：检查节奏与 6 小时缓存、302 只读兜底与「手动下载」入口。
3. **P2**：托盘动态菜单项、进度细化（已下载/总大小）。
4. **P3**：可选代理设置（需评审）、文档同步与发布 0.4.0（含 `RELEASE_NOTES.md`）。

## 9. 风险与取舍

- **长期不打开主窗口的用户可能错过更新**：绿色胶囊只在主窗口可见，托盘菜单项与设置页是补充；如后续需要，可加「托盘图标绿点」但不做气泡。
- **胶囊紧贴版本徽标的代价**：标题行在窄窗口下元素变多（标题、徽标、胶囊、立即同步、隐藏到托盘）。compact 宽度下胶囊收成两字「更新」，并优先于版本徽标被压缩（徽标可降到只显示 `v0.3.9` 的紧凑形态）。
- **6 小时缓存与现有 24 小时节流文档冲突**：必须在同一次发布内同步修订，避免文档与行为不一致。
- **302 解析依赖 GitHub 行为**：仅作提示用途，失败静默，不引入新的信任假设。
- **代理设置可能被当作通用代理**：限定更新模块、限定协议、禁止内嵌凭据，日志与诊断包一律不记录。
- **绿色按钮的视觉权重**：需与「立即同步」按钮区分（同为绿/蓝系），避免用户误点；文案必须显式带版本号。
- **一键全自动的心理预期**：点击后程序会在下载验证完成时自行退出。必须靠按钮文案与细行把「点击后将自动下载并重启」讲清楚；下载过程可随时关程序放弃，避免用户觉得被偷袭。
- **点击后立即退出的风险**：若用户正在编辑未保存的设置，退出会丢弃未保存修改。缓解：沿用现有「未保存修改」提示逻辑，并在细行提示；不做安装前二次确认（按需求）。

## 10. 明确不做

- 不做静默安装、不做后台强制更新、不绕过 UAC。
- 不做差分更新、不做多通道（stable/beta）、不做自动回滚。
- 不引入 Tauri/WebView，不引入独立更新服务。
- 不为「更新」单独新增状态框架或任务系统（沿用 `UpdateController` 与 `OperationGate`）。
- 不使用任何未签名信息驱动安装。
