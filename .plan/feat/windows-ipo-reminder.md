## 1. 目标

开发一个随 Windows 用户登录后自动启动、常驻系统托盘的 A 股新股申购提醒程序。

当天存在可申购新股时，程序为每只新股建立独立提醒任务。只要用户没有明确点击“确认已申购”，提醒就持续存在：白天默认每小时提醒一次，越接近用户设置的申购截止时间提醒越频繁。关闭弹窗、Toast 自动消失、锁屏、休眠或重启程序，都不能视为已经申购。

程序只记录用户的人工确认，不声称已经验证券商订单是否成功。

## 2. 产品边界

### 2.1 首版包含

- 覆盖沪市、深市、创业板、科创板、北交所公开发行的新股申购信息。
- 系统托盘常驻、登录自启动、单实例运行。
- 自动获取申购日、股票代码、申购代码、简称、发行价、申购上限、申购单位、状态及公告链接。
- 按沪市、深市、北交所分别维护官方申购时段，并允许配置券商实际受理时间和安全截止时间。
- 为同一天的每只新股分别维护“待确认/已确认”状态。
- 未确认时按时间升级提醒频率。
- 申购日期、代码、状态等关键字段发生变化时立即提醒。
- 下载正式公告并定向提取申购日期、申购代码、发行价、申购上限和发行状态；解析失败时进入人工核验状态。
- 使用持久化提醒队列，保证程序崩溃、休眠或重启后不漏掉到期提醒。
- SQLite 本地持久化，电脑重启后继续未完成任务。
- 显示数据最后更新时间、来源和冲突/过期状态。
- 每日主动报告程序及数据源健康状态，使“今日无新股”和“程序没有正常工作”可明确区分。
- 提供同步记录、提醒记录和人工确认记录，方便排查漏报。

### 2.2 首版不包含

- 券商登录、自动申购、自动下单或订单结果核验。
- 读取用户持仓、市值、可申购额度或中签结果。
- 给出收益预测、破发概率或申购建议。
- 手机端和跨设备确认同步。
- 自动把“弹窗已显示”当作“用户已处理”。

## 3. 核心交互

### 3.1 日常状态

程序启动后缩到系统托盘。托盘图标和主面板显示：

- 今日待确认数量。
- 今日已确认数量。
- 下一只新股及下一次提醒时间。
- 最近一次成功同步时间。
- 调度器最近心跳时间，以及各数据源的正常、陈旧、失败状态。
- 数据源异常或字段冲突提示。

托盘菜单提供：

- 今日申购任务。
- 未来申购日历。
- 立即同步。
- 提醒设置。
- 查看日志。
- 退出程序。

当仍有未确认任务时，退出程序必须显示明确警告，避免误退出。程序无法也不应阻止用户通过任务管理器强制结束进程。

### 3.2 提醒卡片

每张提醒卡片至少显示：

- 股票简称、股票代码、申购代码、交易所/板块。
- 申购日期、发行价、申购上限和申购单位。
- 当前时间、交易所官方申购时段、券商受理时间和用户设置的安全截止时间。
- 北交所任务额外显示全额缴款提示及可能存在的时间敏感配售提示。
- 数据来源、最后同步时间、正式公告入口。
- 数据质量状态：已由公告核验、双源核验、单源待核验、来源冲突或数据陈旧。
- 醒目的说明：“本程序无法验证券商端是否提交成功”。

操作按钮：

- `打开详情`：打开程序详情页和正式公告。
- `稍后处理`：仅关闭本次窗口，后续仍按计划提醒。
- `确认已申购`：进入二次确认。

二次确认文案建议：

> 请确认你已经在券商客户端提交了该新股申购委托；如果券商明确支持申购日当天的开盘前预约申购，也包括当天已经提交的预约委托。本程序不会检查委托是否受理或成交。确认后，本申购日内将停止该股票的重复提醒。未来申购日的任务不能提前确认。

二次确认完成后，记录股票、申购日、确认时间和当时的数据版本。首版不提供容易误触的“一键全部确认”；同日多只股票必须逐只确认。用户可在安全截止时间前从任务历史中撤销误确认，撤销后立即恢复提醒。

### 3.3 确认状态规则

确认键建议使用：

```text
(apply_code, apply_date, issue_event_version)
```

规则：

- 只有完成“确认已申购”的二次确认，任务才进入 `acknowledged`。
- “确认已申购”仅在任务所列申购日当天可用；未来任务即使已进入日历也不能提前确认。
- 关闭窗口、Toast 超时、点击“稍后处理”、应用重启均不改变确认状态。
- 股票改到新的申购日时，原申购日的确认不得沿用，必须生成新任务。
- 股票被正式暂缓、中止或终止发行时，停止申购提醒并发送一次状态变更提示。
- 已确认后，若申购代码、申购日期、发行价格、发行状态或官方申购时段发生变化，任务进入 `acknowledged_needs_review`，恢复提醒并要求用户重新确认。
- 已确认后，若仅上市日、市盈率等非申购关键字段变化，发送一次变更提示，不恢复循环提醒。
- 人工撤销确认后，任务立即回到 `active_unconfirmed`。
- 申购截止时仍未确认，进入 `expired_unconfirmed`，保留红色未完成记录，不再整夜无限弹窗。

## 4. 默认提醒策略

所有时间使用 `Asia/Shanghai`。程序必须同时区分“交易所官方申购时段”“券商实际受理时间”和“用户安全截止时间”，不能只保存一个统一的 15:00 截止时间。

截至 2026-08-24，默认市场时段模型如下；具体任务仍以该次正式发行公告为准：

| 市场 | 默认官方网上申购时段 | 特殊处理 |
| --- | --- | --- |
| 沪市主板、科创板 | 09:30–11:30、13:00–15:00 | 开盘前提醒默认设为 09:25 |
| 深市主板、创业板 | 09:15–11:30、13:00–15:00 | 开盘前提醒默认设为 09:10 |
| 北交所 | 09:15–11:30、13:00–15:00 | 显示全额缴款提示；早盘提醒提高优先级 |

首次设置时，用户需为自己使用的券商确认：

```text
broker_accept_start    券商开始接受当日申购或预约申购的时间
safety_cutoff          用户希望完成申购的最晚安全时间
```

首次运行向导必须要求用户确认安全截止时间。方案推荐预置为 14:55，15:00 仅代表当前公告常见的官方申购结束上限，不能承诺券商会受理到最后一刻。用户设置的安全截止时间不得晚于当前正式公告对应的官方结束时间。北交所如果券商支持在 09:15 前接收预约委托，可额外配置该时间，并在其前 5 分钟提醒。

默认策略如下，后续允许在设置页调整。频率升级以 `safety_cutoff` 为基准使用相对时间，不再把 14:00、14:30、14:50 写死：

| 时间点或时间段 | 默认行为 |
| --- | --- |
| 申购日前一日 20:00 | 提前提醒一次，展示次日待申购列表 |
| 申购日 08:00 | 发送数据和程序健康摘要，明确今日任务数量 |
| 申购日 08:30 | 首次强提醒 |
| 对应市场上午开盘前 5 分钟 | 未确认时发送开盘前强提醒；沪市默认 09:25，深市/北交所默认 09:10 |
| 上午开盘至 11:19 | 未确认时至少每 60 分钟提醒一次 |
| 11:20 | 上午官方时段结束前提醒一次 |
| 12:55 | 下午官方时段恢复前提醒一次 |
| 下午官方时段恢复至截止前 60 分钟 | 未确认时至少每 60 分钟提醒一次 |
| 截止前 60 分钟至截止前 30 分钟 | 未确认时每 15 分钟提醒一次 |
| 截止前 30 分钟至截止前 10 分钟 | 未确认时每 5 分钟提醒一次 |
| 截止前 10 分钟至安全截止时间 | 未确认时每 2 分钟提醒一次，并保持托盘红点 |
| 到达安全截止时间 | 最后一次告警，标记为“截止时仍未确认” |

默认安全截止时间为 14:55，因此三个升级边界分别是 13:55、14:25、14:45，14:55 发送最终告警。若用户明确设置为 15:00，则边界分别是 14:00、14:30、14:50。每个等级的起点必须生成提醒，等级内再按对应间隔生成；计划重算后要取消尚未投递的旧时间点，不能让旧截止时间继续触发。

补充规则：

- 北交所任务在 `broker_accept_start` 和上午官方开盘前各安排一次高优先级提醒；早盘提醒不因已有下午升级提醒而省略。
- 北交所网上发行通常先按有效申购总量比例配售；不足 100 股的余股部分再按申购数量优先、数量相同时申购时间优先处理。界面只提示“尽早提交可能影响余股顺序”，不得笼统描述为整笔申购都按时间优先。
- 官方午间休市期间不机械维持整点节奏，使用 11:20 和 12:55 两个边界提醒；若券商支持午间预埋委托，用户仍可在卡片中确认。
- 程序在某个提醒时刻之后才启动时，立即补发当前等级的提醒，不补发一串历史弹窗。
- 电脑从休眠或锁屏恢复后，立即同步并检查是否存在逾期未确认任务。
- 同一只股票、同一调度时刻只生成一次提醒，防止应用重启造成重复轰炸。
- 同日多只股票可以合并声音/Toast，但应用内必须保留逐只确认卡片。
- Windows Toast 可能被专注助手或系统策略抑制，因此它只作为辅助通道；应用自己的非模态提醒窗口才是可靠主通道。
- 截止前 30 分钟使用置顶但不抢占键盘焦点的小窗；截止前 10 分钟可以增加声音和任务栏闪烁，均可配置。

## 5. 数据获取方案

### 5.1 总体策略

使用“全市场发现源 + 交易所/法定披露源核验 + 最新正式公告裁决”的多源模式：

```text
东方财富全市场列表
        ↓ 发现候选并补齐常用字段
上交所 / 巨潮资讯 / 北交所结构化接口
        ↓ 交叉核验
最新正式发行公告
        ↓ 冲突时作为最终依据
标准化记录 + 字段来源 + 原始响应
```

任何一个接口失败都不能解释成“今天没有新股”。保留最近一次有效数据并标记为陈旧，继续执行已有提醒，同时在托盘显示同步异常。

数据源必须同时标注“内容权威性”和“技术契约稳定性”。官方内容不等于官方开放 API；下列 JSON、JSONP 和公告检索地址均按公开网页后端适配，不能假设字段、分页或访问策略永久不变。

| 来源 | 覆盖与角色 | 内容权威性 | 技术契约 | 失败时处理 |
| --- | --- | --- | --- | --- |
| 东方财富新股列表 | 沪深北全市场候选发现、补齐常用字段 | 第三方 | 公开 Web JSON，未承诺稳定 | 使用官方源和最近缓存，不得判定“无新股” |
| 上交所结构化列表 | 沪市主板、科创板交叉核验 | 官方 | 公开网页查询接口，可能要求请求头并可能改版 | 标记源异常，转公告检索和缓存 |
| 上交所正式公告 | 沪市字段与发行状态最终依据 | 官方原文 | 公告查询页/PDF；内容权威但发现接口可能变化 | 保存已下载原文，允许人工定位新公告 |
| 巨潮新股列表 | 深市主板、创业板交叉核验 | 法定披露平台 | 公开网页接口，字段名较非语义化 | 转公告检索、东方财富和缓存 |
| 巨潮正式公告 | 深市字段与发行状态最终依据 | 法定披露原文 | 公告检索 POST + PDF | 保存已下载原文，允许按代码/简称重搜 |
| 北交所新股列表 | 北交所候选发现与状态核验 | 官方 | Session + JSONP + 分页，稳定性较低 | 转发行详情页、公告 PDF 和缓存 |
| 北交所正式公告 | 北交所字段、资金和配售规则最终依据 | 官方原文 | 详情 API → `9533` 披露检索兜底 → 官方 PDF；需 Session/Cookie | 保存已下载原文；身份不匹配或解析失败时进入人工核验 |

每个采集器都必须输出统一健康信息：HTTP 结果、内容类型、耗时、记录数、分页数、字段集合指纹、原始内容哈希、抓取时间和解析错误。启动时以及每天至少一次执行轻量契约探测；字段集合或记录规模异常时先报警，不把异常响应写成有效空结果。

#### 5.1.1 2026-08-24 在线契约快照

以下是 2026-08-24 从开发机执行的轻量探测与隔离 .NET 诊断结果，只作为当前解析契约和 fixture 基线，不代表网站承诺长期稳定：

| 来源 | HTTP/内容类型 | 当前顶层结构 | 实现约束 |
| --- | --- | --- | --- |
| 东方财富 | `200 text/plain;charset=UTF-8` | JSON：`result.pages`、`result.data[]` | 不能只接受 `application/json`；正文必须先通过 JSON 和业务字段校验 |
| 上交所 | `200 application/json;charset=UTF-8` | JSON：`pageHelp.data[]` | 需要正常 `User-Agent` 与 IPO 页面 `Referer`；校验分页和 `actionErrors` |
| 巨潮资讯 | `200 application/json;charset=UTF-8`，传输可能为 gzip/br | JSON：`code=200`、`data[]` | HttpClient 必须自动解压；HTTP 200 后仍须校验业务 `code`、字段集合和明细数量 |
| 北交所 | 落地页 `200`；Session POST 为 `200 text/html;charset=utf-8` | JSONP：`ipoCb([{ listInfo: { content, totalPages } }])` | 必须先建 Session/Cookie；`text/html` 在该端点是当前正常类型，但正文仍须严格校验 callback、JSON 和分页 |
| 北交所公告 | 详情/披露查询返回 JSONP；正式文件返回 `application/pdf` | 详情 `infoDetailResult.do`；披露 `zoneInfoResult.do`；PDF 位于官方披露域名 | 首次访问可能 302 到自身并设置 `C3VK`；使用 CookieContainer 正常跟随，不绕过访问控制；严格校验发行人身份和附件类型 |
| 巨潮公告 | 正常响应为压缩 JSON；健康空结果可能为 `announcements=null` 且两个总数均为 0 | 正常契约含 `announcements[]` 或可证明的健康空结果 | 使用独立 Cookie 会话、来源内串行节奏和业务字段校验；非零计数、缺失计数或非法类型视为契约异常并输出脱敏摘要 |
| 上交所公告附件 | URL 可为 `.pdf`，但真实请求可能返回约 3.8 KB 的动态错误页 | 正常文件应具有 `%PDF` 签名；错误页哈希可能变化 | 以响应内容和文件签名裁决；错误页受控进入来源退避和 `ManualReviewRequired`，保留官方入口 |

因此内容类型校验必须按数据源配置允许集合，不能使用全局“必须为 JSON”。若正文出现 HTML 登录页/WAF 页，需结合 callback、文件签名、首字符、顶层字段和 schema fingerprint 判为失败。四个主采集器和本轮预期公告 Provider 均已由严格诊断实际尝试；巨潮健康空结果和上交所伪 PDF 均已形成脱敏 fixture、自动化回归和可追溯的受控降级，当前没有未覆盖的数据契约缺口。

任务以公告中的 `apply_date` 为准，不依赖“周一至周五”猜测交易日。周末和节假日可以降低同步频率，但不能因为本地日历判断而跳过公告变更检查。

#### 5.1.2 首版数据渠道决策（已冻结）

首版运行时不需要任何付费 Token，也不把 GitHub 项目、AKShare 或 Tushare 当作生产必需依赖。固定路由如下：

| 层级 | 首选渠道 | 程序用途 | 是否允许单独作最终结论 |
| --- | --- | --- | --- |
| 候选发现 | 东方财富 `RPTA_APP_IPOAPPLY` | 一次发现沪、深、北候选并补齐展示字段 | 否 |
| 沪市核验 | 上交所 IPO 列表、公司公告查询、正式发行公告 PDF | 核验主板/科创板任务、状态和关键字段 | 正式公告可以 |
| 深市核验 | 巨潮新股列表、历史公告查询、深交所静态公告 PDF | 核验主板/创业板任务、状态和关键字段 | 正式公告可以 |
| 北交所核验 | 北交所公开发行列表/详情、披露检索、正式公告 PDF | 核验北交所任务、资金要求、代码与配售规则 | 正式公告可以 |
| 故障兜底 | 本地最近一次有效事件、原始响应和已下载公告 | 网站临时失败时继续已有提醒并显示陈旧/异常 | 只能维持旧任务，不能证明“今日无新股” |

实现上每个来源独立适配、独立限速、独立退避，统一输出 `CollectorResult`；合并器只接受已经通过来源契约校验的数据。正式公告是字段冲突的最终依据，但“公告检索接口成功返回”与“已成功下载并识别正确公告”必须分别记录，不能合并成一个布尔值。

同步节奏统一按第 9 节执行：启动/唤醒立即同步、平时每 30 分钟、存在当日未确认任务时每 10 分钟检查状态和新公告。此处是数据刷新节奏，不等于用户提醒频率。所有请求加入小幅随机抖动，同一来源连续失败时指数退避，但至少保留低频健康探测。

公开网页可访问不代表存在长期开放 API 或允许无限制再分发。首版只为本地提醒保存完成核验所需的最小数据和公告证据，不做批量镜像或对外转售；不绕过验证码、登录、WAF 或其他访问控制。若以后公开分发或商业化，发布前需单独复核各站点当时的使用条款、访问频率和数据再利用边界。

### 5.5 北交所核验

结构化接口为 JSONP：

```text

statetypes=1
page=0
isNewThree=1
sortfield=purchaseDate
sorttype=desc
```

采集器先访问公开发行页面建立 Session/Cookie，再请求接口并解析 JSONP。主要字段：

```text
id, fxCode, stockCode, stockName, issuePrice, peRatio,
purchaseDate, issueResultDate, enterPremiumDate,
initialIssueAmountW4, suspendDate, terminationDate
```

北交所必须分别保存当前证券代码、本次申购代码和历史新三板代码。自 2025-10-09 起北交所存量股票已全面切换为 `920` 代码；新增上市公司此前也已逐步采用 `920` 代码完成询价、申购和上市。对 2024 年以前的历史响应，`fxCode`、`stockCode` 仍可能分别代表当次发行代码和旧挂牌代码，因此不能只看前缀，也不能无条件把 `fxCode` 同时写入 `security_code` 与 `apply_code`。合并时优先使用本次正式发行公告，并保留新旧代码映射作为别名。

北交所采集和提醒还必须遵守：

- JSONP 响应必须按分页元数据遍历，不能只假设第 0 页包含全部有效任务。
- `bseinfo.net` 的列表与 JSONP 属于公开网站后端，不是承诺稳定的开放 API；裸请求可能被 WAF 拒绝。采集器必须先建立 Session、使用合理请求头和限速，并同时监测 `bse.cn`/`bseinfo.net` 官方披露入口。访问受限时转公告检索和缓存，不尝试绕过访问控制。
- 日期对象优先读取其中的 epoch `time` 并转换为上海时区，不能直接按零起始月份和偏移年份拼接日期。
- UI 明确显示北交所通常需要在申购时全额缴付资金，不得套用沪深市值申购提示。
- 当剩余股票的配售规则涉及申购时间先后时，在卡片中显示“尽早提交”的规则提示，但不把它描述为收益建议。
- 券商可能在官方时段前接受预约委托，因此 `broker_accept_start` 只能由用户设置或券商公开通知提供，不能由交易所时间自动推算。

公告详情入口只负责提供合法数字 `id`：

```text
https://www.bseinfo.net/newshare/listofissues_detail.html?id=<id>
```

正式公告的首选发现接口：

```text
GET https://www.bseinfo.net/newShareController/infoDetailResult.do
callback=ipoDetailCb
id=<详情页数字 id>
page=<0..>
pageSize=100
```

详情接口失败、契约损坏或没有找到身份匹配的正式公告时，使用公开发行披露检索兜底：

```text
GET https://www.bseinfo.net/disclosureInfoController/zoneInfoResult.do
callback=ipoDisclosureCb
disclosureTypes[]=9533
page=<0..>
companyCd=<证券代码、申购代码、历史代码或公司简称>
startTime=<yyyy-MM-dd>
endTime=<yyyy-MM-dd>
keyword=
isLink=1
```

两条路径分别最多读取 10 页。正式公告 PDF 通常位于 `bseinfo.net/disclosure/`；发现器必须同时满足以下约束后才能接受附件：

- 证券代码、申购代码或历史代码至少一项与当前事件匹配。
- 公司简称匹配，或公告标题具有可验证的发行人前缀。
- 发布日期在查询范围内，标题属于本次发行相关公告。
- 附件必须为 PDF，URL 必须是 HTTPS，主机仅允许 `bseinfo.net` 或 `bse.cn`。
- 路演公告、审计报告、风险特别公告等非正式发行文件不得作为字段最终依据。
- 公告稳定 ID 从 PDF 文件名生成，避免列表顺序或临时查询参数变化造成重复版本。

北交所站点当前可能先 302 到自身并设置 `C3VK` Cookie；BSE 专用 HttpClient 使用独立 CookieContainer 和自动解压后再继续请求，不尝试绕过验证码或其他访问控制。2026-08-24 的固定在线样本为华汇智能 `920289`、详情 id `346`、正式 PDF `https://www.bseinfo.net/disclosure/2026/2026-08-20/1787216709992_052262.pdf`。该样本已经完成真实 .NET 下载、哈希、解析和字段证据核验，结果保存在 `artifacts/diagnostics/bse-sample-20260824.json`。

### 5.6 公告监控与定向解析

标题匹配至少覆盖：

```text
发行安排及初步询价公告
发行公告
暂缓发行
中止发行
终止发行
延期发行
重新启动发行
网上发行申购情况及中签率公告
网上中签结果公告
上市公告书
```

正式公告既然被定义为最终裁决源，首版就必须完成最小可用的公告解析闭环：

```text
发现公告
  → 下载原文件
  → 校验响应类型和文件签名
  → 保存公告编号、发布时间、URL 和 SHA-256
  → 提取可复制文本
  → 定向解析关键字段
  → 计算字段级置信度
  → 合并或进入人工核验
```

首版定向解析字段：

```text
申购日期
股票代码
申购代码
发行价格
网上申购上限
申购单位
官方申购时段
资金缴付方式（含北交所全额缴款）
延期、暂缓、中止、终止、重新启动状态
```

规则：

- 不要求首版实现通用 PDF 语义理解，但上述字段必须有可测试的定向提取器。
- 文本型 PDF 直接提取；扫描件或提取失败时进入 `manual_review_required`，OCR 可以作为后续增强。
- URL、扩展名和列表中的附件类型只能作为提示；PDF 必须通过 `%PDF` 文件签名校验，HTML/WAF/错误页必须作为下载失败处理。
- 只有高置信度且公告身份匹配的字段才能自动覆盖结构化来源。
- 同一公告重复下载时按内容哈希去重；URL 不变但文件内容变化时建立新版本并重新解析。
- 解析结果必须保存原始文本片段位置，详情页可以让用户回看依据。
- 人工覆盖必须记录覆盖字段、值、理由、依据公告、操作时间和有效事件版本；新发行版本不得沿用旧人工覆盖。
- 公告无法解析时不得删除已发现任务，继续提醒并突出显示“正式公告待人工核验”。

### 5.9 “今日无新股”的判定规则

“接口返回空数组”不等于“今日无新股”。同步结果必须先归入以下状态之一：

```text
healthy_nonempty  契约正常且返回有效任务
healthy_empty     契约正常且返回可解释的空结果
degraded_cached   当前抓取失败，继续使用最近有效缓存
unknown           没有足够证据判断有无任务
```

只有同时满足以下条件，UI 才能显示绿色“今日无新股”：

1. 至少一个全市场发现源完成有效契约校验；
2. 每个已启用市场至少一个官方结构化源或公告检索源成功完成本次覆盖区间查询；
3. 计数接口与明细不存在未解释差异，且没有缓存中的活动/未来任务被当前空响应异常移除；
4. 最后成功时间未超过当前场景的陈旧阈值。

条件不满足时必须显示“暂未获取到申购任务，数据状态未知/陈旧”，并保留缓存任务和原提醒计划。HTTP 200 但内容类型错误、验证码页、登录页、字段集合突变、分页中断或解析后记录数异常，一律归为契约失败，不能归为 `healthy_empty`。

每次真实联网诊断要保存源名称、请求时间、状态码、内容类型、schema fingerprint、页数、记录数、原始哈希和脱敏错误摘要，以便判断是“确实为空”还是“采集器失效”。

## 6. 数据合并和容错规则

字段级优先级：

1. 最新正式发行公告。
2. 对应交易所/巨潮/北交所结构化数据。
3. 东方财富全市场数据。
4. 可选备用源。

必须遵守：

- 保存每个源的原始值、抓取时间、发布时间和内容哈希。
- 官网空值不能覆盖已有的有效非空值。
- 统一识别 `null`、空字符串、`-`、`--`、`N/A` 等缺失标记；数值 `0` 是否有效必须按具体字段判断，不能全局当作空值或有效值。
- 新响应必须先通过 HTTP 状态、JSON/JSONP 格式、字段结构和记录数量合理性检查。
- 请求失败、返回空页、字段改名和真正“无新股”是四种不同状态。
- 两个非空来源出现关键字段冲突时设置 `data_conflict=true`，保留双方值并优先检查公告。
- `security_code`、`apply_code`、`legacy_code` 分开保存。
- 申购单位、申购上限及其单位必须随来源保存，标准化时显式换算，禁止硬编码。
- 所有日期落库前转为上海时区的本地交易日期。
- 正式延期或重新发行应创建新的事件版本，不能复用旧确认记录。
- `getToDayNewStockCount` 等计数接口只用于一致性检查，不能替代任务明细；计数与明细不一致时发出采集质量告警。

任务不应等待所有展示字段齐全才创建。字段完整度分为：

```text
建立候选任务所需：exchange + security_code/稳定候选标识 + apply_date + status
申购日前必须补齐：apply_code + 官方申购时段
允许延迟补齐：issue_price + max_apply_qty + lot_size + listing_date 等
```

如果申购日早上仍缺少申购代码或官方时段，保留任务并升级为红色 `manual_review_required`，不能静默忽略。

每条任务维护独立的数据质量状态：

```text
announcement_verified  已由正式公告核验
multi_source_verified  两个及以上独立来源一致
single_source          只有一个有效来源
data_conflict          非空关键字段发生冲突
stale                  有效数据超过陈旧阈值
manual_review_required 公告或必要字段需要人工核验
```

确认后的字段变更分级：

- 申购代码、申购日期、发行价格、发行状态或官方申购时段变化属于关键变化，设置 `acknowledged_needs_review` 并恢复提醒。
- 申购上限、申购单位变化发送高优先级警告，由用户重新查看，但是否重启循环提醒作为可配置安全策略，默认重启。
- 上市日、市盈率等非申购关键字段变化只发送一次普通提示。

## 7. 技术架构

首版固定使用 C#、.NET 10 LTS 和 WPF，并锁定 SDK 与 NuGet 依赖版本。Windows 托盘、登录启动、置顶提醒窗口、电源恢复事件、单实例和本地安装都由桌面应用完成；数据接口均为 HTTP/JSON，不需要为了采集层引入 Python 运行时。

建议的关键依赖边界：

```text
WPF                                            主界面、托盘、非模态置顶提醒窗
Microsoft.WindowsAppSDK                        提供 Microsoft.Windows.AppNotifications API
Microsoft.Data.Sqlite                          SQLite 访问
TimeProvider（.NET 内置）                       可测试时钟与调度时间来源
```

自定义 WPF 提醒窗口是主提醒通道，Windows Toast 是辅助通道。Toast 只能打开应用中的对应股票卡片，不能直接把任务标记为已确认；用户必须在应用内点击“确认已申购”并完成二次确认，最终调用幂等确认命令。

```text
WPF 托盘、提醒窗口与 Toast（Toast 仅打开任务）
        ↑
Delivery Worker ← Durable Reminder Outbox
        ↑
Reminder Engine（市场时段、频率升级、确认状态）
        ↑
Scheduler（定时、心跳、休眠恢复、错过任务补偿）
        ↑
IPO Application Service
   ├─ Eastmoney Collector
   ├─ SSE Collector
   ├─ CNINFO Collector
   ├─ BSE Collector
   ├─ Announcement Downloader / Parser
   └─ Reconciler / Manual Override
        ↓
SQLite（业务数据、原始响应、公告、队列、同步与提醒日志）
```

Windows 进程形态：

- 使用普通桌面托盘程序，不使用 Windows Service；Service 位于隔离会话，不适合直接向当前桌面显示交互窗口。
- 使用命名 Mutex 保证单实例。
- MVP 使用“用户登录时启动”的每用户计划任务，并配置异常退出后重启；任务必须运行在用户交互会话中。
- 应用退出和操作系统关机时安全提交 SQLite 事务。
- 监听系统恢复/网络恢复事件，恢复后立即同步并重算下一次提醒。
- 调度器每分钟写入本地心跳；UI 根据心跳和最后成功同步时间显示程序健康状态。
- 首次运行向导依次确认启用市场、券商可受理时间、安全截止时间、自启动和提醒通道，并执行通知自检，让用户确认普通弹窗、置顶窗口、声音和 Toast 是否可见。
- 技术最低目标固定为 Windows Build 19041、x64；`0.1.0` 实际验证范围为 Windows 11 Pro Build 26200 x64。Windows 10、更多 DPI、远程桌面和多屏组合属于后续扩展验证矩阵，未取得对应证据前不扩大已验证支持声明。

### 7.1 隐私、安全与网络边界

- 所有任务、设置、确认记录、日志和公告缓存默认只保存在当前 Windows 用户的本地应用数据目录。
- 不采集或保存券商账号、密码、短信验证码、持仓、资金和设备内其他金融信息；默认不启用遥测。
- 出站请求限定到配置的数据源域名；正式发行公告使用 HTTPS 原始链接，不执行公告中的脚本或附件程序。
- 不绕过登录、验证码、访问控制或反爬限制。遇到限制时降低频率、使用缓存并显示数据源异常。
- 日志默认隐藏查询参数中可能出现的令牌；未来增加外部推送时，Webhook/Token 必须使用 Windows 凭据保护或 DPAPI 加密保存。

## 9. 同步调度

默认同步节奏：

- 应用启动、网络恢复、电脑唤醒时立即同步。
- 06:00 至 22:00，每 30 分钟同步一次候选列表。
- 申购日前一日 20:00 执行一次跨源核验；申购日 08:00 再执行一次最终核验和健康摘要。
- 当天存在未确认申购任务时，08:00 至安全截止后 10 分钟，每 10 分钟同步一次状态和最新公告。
- 普通 30 分钟同步加入 0–90 秒随机抖动；申购日活动窗口的 10 分钟同步抖动不超过 20 秒，避免削弱临近截止检查。
- 单源失败按 1、2、4、8、15、30 分钟退避并封顶 30 分钟，成功一次后重置；遇到 `Retry-After` 时优先遵守服务端值。其他数据源继续运行，应用重启不得把所有失败源同时打回高频重试。
- 连续失败或有效数据超过设定陈旧阈值时，托盘变为黄色/红色并明确提示“数据未更新”，但不删除已有任务。

默认健康阈值：

```text
普通日期：最后成功同步超过 2 小时为黄色，超过 6 小时为红色
任务进入未来 24 小时：核心来源超过 60 分钟未成功为红色
全部来源失败：立即发送本地故障告警
申购日 08:00 仍缺 apply_code/官方时段：manual_review_required
```

每天 08:00 主动发送一条健康摘要，无论当天是否有新股：

```text
程序运行正常 / 调度异常
今日待申购 N 只
各数据源最后成功时间
公告核验、冲突和待人工核验数量
```

如果只有单一来源但已经得到申购日，仍然创建和执行提醒，只把数据质量标记为 `single_source`。来源不完整只能降低置信度，不能压制提醒。

接口调用需要设置合理超时、限速、重试上限和稳定的请求头。不要绕过验证码、登录限制或站点访问控制；接口不可用时降级到缓存和其他公开源。

### 9.1 系统时间与调度可靠性

- 数据库存储统一使用 UTC 时间戳，申购日期和界面显示统一按 `Asia/Shanghai` 转换；不得直接依赖 Windows 当前显示时区计算交易日。
- 调度同时使用可注入 `TimeProvider` 和单调递增计时基准检测系统时间跳变。启动、唤醒、会话解锁、网络恢复和系统时间变更后，立即重算计划并执行“只补当前等级”的恢复规则。
- 启动和每日健康检查读取 Windows 时间服务状态，并在可用时交叉比较至少两个独立 HTTPS 响应的 `Date` 头。偏差超过 2 分钟显示黄色警告，超过 5 分钟显示红色告警。
- 时间异常不能把任务自动标记为已完成，也不能删除 pending outbox。程序继续保留任务、提示用户校准系统时间，并在校准后重新计算尚未投递的计划。
- 手工把时间向前或向后调整时，同一 `dedupe_key` 不得重复投递；若跨过多个等级，只投递调整后当前最高等级的一次提醒。

## 10. 状态机

```text
discovered
   ↓ 申购日和稳定候选标识可用
scheduled
   ↓ 到达申购日且未确认
active_unconfirmed ──用户确认──> acknowledged
   │
   ├─正式暂缓/中止/终止──> suspended_or_cancelled
   ├─申购日变更──────────> superseded（新版本回到 scheduled）
   └─到达截止时间────────> expired_unconfirmed

acknowledged
   ├─关键申购字段变化────> acknowledged_needs_review
   │                              ├─用户重新确认──> acknowledged
   │                              └─到达截止时间──> expired_unconfirmed
   └─用户撤销确认────────> active_unconfirmed
```

`data_quality_status` 与业务状态机是两个独立维度；`single_source`、`data_conflict` 或 `manual_review_required` 不得自动把任务变成完成状态。

只有 `acknowledged`、正式取消/暂停状态或已到截止时间能结束当日循环提醒。`acknowledged_needs_review` 必须恢复循环提醒。数据源暂时不可用不能推动状态机进入完成状态。

### 12.2 固定样本与真实联网测试规则

- 固定 fixture 必须来自真实响应或正式公告的脱敏副本，保留抓取日期、来源、内容哈希和预期字段；不得只用为了通过测试而手写的最小 JSON。
- 在线测试只用于契约探测和最终诊断，不参与普通单元测试，不因网络波动让 CI 随机失败。
- 在线同步使用临时应用数据目录和临时数据库；结束后导出诊断摘要，检查缓存、公告和日志中没有券商凭据或无关个人信息。
- 在线诊断的成功条件覆盖本轮实际尝试的主 Collector、公告 Provider、公告下载签名和 SQLite 完整性；受控降级必须显式记录 `manual_review_required`，不能只看顶层 `success` 或主来源计数。
- 对没有近期真实申购样本的市场，使用已保存的历史正式公告回放；真实发行日观察作为发布候选后的运行验证，不用无限期阻塞本地可交付测试版。

## 14. 已知限制

- 没有券商接口就无法知道用户是否真的提交成功、是否具备市值额度或订单是否被拒绝；“确认已申购”完全是用户自我确认。
- 电脑关机、程序被强制结束或 Windows 会话未登录时无法弹窗；恢复后只能补发。
- Windows Toast 可能受专注助手影响，因此不能把 Toast 送达作为唯一提醒保证。
- 网站公开接口不是正式稳定 API，字段和访问策略可能变化，采集器必须可独立替换并有结构异常告警。
- 券商的实际受理截止时间可能早于交易所时间，必须由用户在首次设置时确认。
- 券商提前接受预约委托的时间可能变化，程序只能使用用户配置或公开通知，不能保证预约最终转成有效申购。
- 北交所所需全额申购资金、实际冻结金额和是否受理无法在不连接券商账户的前提下验证。
- 扫描版、加密版或版式异常公告可能无法自动解析，必须进入人工核验，不能伪造高置信度结果。

### 16.1 安装、升级与卸载策略

- 每用户安装目录与本地数据目录分离；升级程序文件不得覆盖数据库、公告缓存、备份和用户设置。
- 安装包默认注册“用户登录时启动”的计划任务，只在首次向导完成且用户开启自启动后启用；便携版不自动注册。
- 升级前创建一次数据库备份，运行 migration 后校验 schema 和关键表；失败时保留旧程序与备份并给出恢复说明。
- 普通卸载默认保留本地数据，并提供“同时删除本地数据”的显式复选项和二次确认。静默卸载不得默认删除用户确认记录。
